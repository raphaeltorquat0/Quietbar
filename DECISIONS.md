# Decisões

Registro das escolhas feitas onde a especificação era ambígua. Regra geral: na dúvida,
a opção mais conservadora (menos escrita no fone, menos permissão, menos dependência).

| # | Decisão | Motivo |
|---|---|---|
| 1 | **Um único `Package.swift` na raiz**, com os targets em `Packages/MDRKit`, `Packages/MDRTransport`, `Packages/MDRSession` e `Tools/mdr-cli` | Um pacote por módulo obrigaria dependências locais cruzadas e três `Package.resolved`. Um só pacote mantém `swift test` único e o app consome os produtos pelo `project.yml`. |
| 2 | **A raiz do repositório é o diretório de trabalho** (sem subpasta `Quietbar/`) | Evita um nível extra sem conteúdo. |
| 3 | **RFCOMM assíncrono** (`openRFCOMMChannelAsync` + delegate), nunca o `openRFCOMMChannelSync` | A variante síncrona bloqueia a thread do run loop e trava a UI se o fone demora. |
| 4 | **App Sandbox: funciona e é o padrão do release** | `--selftest` passou com e sem sandbox contra o WH-1000XM5 real (fw 2.5.1): `phase=ready`. O build de desenvolvimento usa `Quietbar.entitlements` (sem sandbox) para facilitar debug; `scripts/release.sh` assina com `Quietbar-Sandbox.entitlements` (`SANDBOX=0` desliga). Os perfis por Wi-Fi dentro do sandbox **não** foram verificados em hardware. |
| 5 | **ACK: espera de 1 s, até 3 tentativas, backoff 150 ms × 2ⁿ**; resposta de GET espera 3 s | Valores de `Session.Options` (`Packages/MDRSession/Sources/MDRSession/Session.swift`). O fone retransmite a mesma sequência quando perde ACK; reenviar com o mesmo `seq` é idempotente. |
| 6 | **Auto power off: SET com último byte `00`** | Divergência [M]×[G] (ver `docs/PROTOCOL.md` §5). [M] tem evidência em XM5 via [L]. Conferência manual em `docs/HARDWARE_TEST.md`. |
| 7 | **Multiponto via General Setting (D2 = `MULTIPOINT`)** + alerta de confirmação repassado ao usuário | No app, o alerta do fone vira um diálogo "Continuar/Cancelar" (`App/Sources/Components.swift`). No `mdr-cli set`, o alerta que chega logo após o comando do próprio usuário é respondido como positivo. |
| 8 | **Gadgetbridge (AGPL) só como fonte de bytes** | Nenhuma linha de código copiada; apenas vetores de teste (sequências de bytes) usados para validar o parser. O código do Quietbar permanece sob licença própria. |
| 9 | **Sem Developer ID → release assinado ad-hoc** | `scripts/release.sh` aceita `SIGN_IDENTITY` e, se `NOTARY_PROFILE` existir, notariza e grampeia. Sem isso, o usuário precisa liberar o app em Ajustes › Privacidade e Segurança na primeira abertura. |
| 10 | **Bateria em segundo plano: checagem a cada 15 min** (ajustável) | Com a UI fechada o canal fica solto para não segurar o fone; o timer abre o canal só para ler a bateria, e só se o fone estiver conectado no sistema. |
| 11 | **Volume 0–30** | Faixa aceita pelo XM5; o SET satura em vez de rejeitar. |
| 12 | **Botão personalizável (função `0xF3`) não é exposto no XM5** | O `dump` real do XM5 não anuncia `0xF3`. A UI só mostra o que o fone anuncia; o perfil de fallback `MDRCapabilities.wh1000xm5` é a lista real do `dump`. |
| 13 | **Presets de EQ sem nome vêm com nome local** | O XM5 não envia nomes; o app usa a tabela de nomes conhecida por id e mostra o id cru quando não conhece. |
| 14 | **Nenhum `set` no fone durante o desenvolvimento sem pedido explícito** | Só `dump` (somente leitura) foi executado no aparelho. Os SETs foram validados contra o fake de `MDRSession` e ficam para o roteiro de `docs/HARDWARE_TEST.md`. |
| 15 | **Popup de conexão espera bateria e modo por até 3 s**; sem eles, mostra só o nome | Evita popup vazio. Enquanto o popup está na tela ele conta como UI aberta, então o canal é liberado 15 s depois que ele some. |
| 16 | **Conexões avisadas nos primeiros 3 s após abrir o app não mostram popup** | Ao registrar `register(forConnectNotifications:)`, o IOBluetooth avisa também das conexões já existentes; isso não é "acabou de conectar". |
| 17 | **`mdr-cli popup` usa `DistributedNotificationCenter` sem `userInfo`** | Funciona com o app em sandbox (o sandbox bloqueia `userInfo` em notificações distribuídas). |
| 18 | **Proximidade por Fast Pair: investigada, não implementada** | `mdr-cli ble-scan` em 2026-10-29, com o XM5 ligado e conectado ao Mac: um único anúncio `0xFE2C` por perto, `00 30 00 00 00 21 16 06` a −52 dBm. Pelo formato, é o modo **não descobrível** (filtro de account key vazio + salt), **sem model ID**, com endereço BLE aleatório, então não dá para atribuí-lo ao XM5. O modo de pareamento (que traria o model ID) não foi testado porque exige alguém com o fone na mão; roteiro em `docs/HARDWARE_TEST.md`. Mesmo anunciando, o endereço aleatório só permitiria dizer "um XM5 por perto", não "o seu". |
| 19 | **Modelo 3D procedural é o padrão; `.usdz` do usuário tem prioridade; se ele falhar (inválido ou > 20 MB), volta para o procedural** | O 2D fica para quando o 3D não monta ou o usuário desliga o 3D em Ajustes › Popup. O `.usdz` é copiado para `~/Library/Application Support/Quietbar/` e `*.usdz` está no `.gitignore`. |
| 20 | **Malha neutra (`MeshData`) → RealityKit e SceneKit** | Um gerador, dois renderizadores: `RealityView` no macOS 15+, `SCNView` no 14, export USDZ e snapshot pelo SceneKit, snapshot pelo `RealityRenderer`. O rig de animação só fala "transformação por nome" e "emissão por segmento". |
| 21 | **A entrada gira o yoke inteiro (junta no topo), não a concha dentro do garfo** | Girar 90° a concha dentro do garfo faria ela atravessar os braços. O pino do pivô (eixo Z) fica para dobrar/inclinar. |
| 22 | **Metal "escovado" aproximado com metallic 1 + roughness 0,28, sem anisotropia** | Anisotropia exige tangentes na malha; o ganho visual nesse tamanho não paga. |
| 23 | **Segmentos do anel sem tampas laterais** | Ficam dentro do canal; as tampas não aparecem de nenhum ângulo e custariam 192 triângulos. |
| 24 | **`RealityView` dentro do app não foi conferido visualmente** | Captura de tela bloqueada no ambiente de desenvolvimento. O `RealityRenderer` offscreen usa as mesmas entidades, materiais, IBL e câmera, e o teste de snapshot confere o render do SceneKit a cada `make test`. (Os PNGs de `docs/model/` saíram do repositório: o visualizador ao vivo da aba Desenvolvedor os substitui.) A janela do popup foi conferida pelo `CGWindowList` (painel de 360×186, nível flutuante, canto superior direito, some após 5 s). |
| 25 | **Sandbox ganhou `files.user-selected.read-only`** | Necessário para importar a imagem e o `.usdz` pelo seletor de arquivos. |
| 26 | **Clique direito e Option-clique no ícone via monitor local de eventos** | O `MenuBarExtra` não expõe o `NSStatusItem`. Um `NSEvent` local monitor reconhece cliques na janela do item de status do próprio app e mostra um `NSMenu`. **Risco conhecido:** neste macOS (27) o `CGWindowList` não mostra janela de item de status no processo de nenhum app (eles são desenhados fora do processo), então o monitor pode não ver o clique. Não foi exercitado com clique real (sem automação de UI aqui); roteiro em `docs/HARDWARE_TEST.md` #21. Se falhar, a saída é trocar o `MenuBarExtra` por um `NSStatusItem` próprio com `sendAction(on: [.leftMouseUp, .rightMouseUp])` e painel em `NSPanel`; não foi feito agora porque o prompt exige `MenuBarExtra(.window)`. Enquanto isso: "Sair" continua no painel e a aba Desenvolvedor também se ativa em Configurações › Geral. **Substituída pela #61.** |
| 27 | **Option-clique abre o menu curto com "Ferramentas de desenvolvedor…"** | O prompt da barra pede menu no Option-clique e o da refatoração pede que ele revele a aba Desenvolvedor; o item extra atende os dois. |
| 28 | **Ícone da barra desenhado a partir do SF Symbol `headphones` (template)**: 35 % de opacidade quando o fone não está conectado ao Mac, ponto de badge com bateria ≤ limite do alerta | Não existe símbolo "headphones riscado"; a opacidade num template image é respeitada pela barra. A % ao lado é opcional (Geral). A bateria vem da última leitura, já que o canal é solto 15 s após fechar a UI. |
| 29 | **"Conectar" pede a conexão Bluetooth ao macOS (`openConnection` assíncrono)** antes de abrir o RFCOMM | Sem isso o botão só funcionava com o fone já conectado ao Mac. "Desconectar" (menu) fecha o canal e a conexão do fone com o Mac. |
| 30 | **Control da Central de Controle é um botão (alternar NC ↔ Ambiente), não um toggle com estado** | A extensão roda em outro processo e não fala com o fone; mostrar estado exigiria App Group, que precisa de Team ID (indisponível com assinatura ad-hoc). O botão posta uma notificação Darwin e o app, dono da sessão, executa a ação. Exige o app aberto (ele abre no login). A extensão está registrada no sistema (`pluginkit`); o toque real na Central de Controle não foi testado. |
| 31 | **`make install` registra o login pelo próprio app** (`--register-login-item`) | Só o app pode chamar `SMAppService.mainApp.register()`. Conferido com `sfltool dumpbtm`: `enabled, allowed`. |
| 32 | **`scripts/build-app.sh` compartilhado por `make install` e `scripts/release.sh`**; entitlements do app via `QUIETBAR_APP_ENTITLEMENTS` | Passar `CODE_SIGN_ENTITLEMENTS` na linha de comando do xcodebuild vazaria os entitlements do app para a extensão. Com Developer ID, a extensão é assinada antes do app (de dentro para fora). |
| 33 | **Sandbox: `files.user-selected.read-write`** (antes read-only) | "Exportar USDZ…" e "Exportar…" do log salvam pelo `NSSavePanel`. |
| 34 | **Log do protocolo sempre em memória (últimos 2000 frames)**; arquivo só com "Gravar tráfego" | Assim a aba Desenvolvedor mostra o tráfego sem precisar reconectar depois de ativá-la. |
| 35 | **Teste de tempo de geração do 3D: 50 ms em release, 200 ms em debug** | Medido: 2,4 ms em release e ~45–60 ms em debug (sem otimização, oscilando com a carga). O requisito é de release; o limite de debug só pega regressão grosseira. |
| 36 | **`mdr-cli` mantido para CI e uso avançado**; o código comum (descrição do estado, decodificação de frames, scanner BLE) foi movido para `MDRKit`/`MDRTransport` | O app e a CLI usam a mesma implementação; nenhuma tarefa comum exige terminal além do `make install`. |
| 37 | **Modelo 3D com as proporções do WH-1000XM5** | A primeira versão era um fone genérico; a atual segue o fone que o app controla. Vistas de referência (que não fazem parte deste repositório) serviram só para proporções e silhueta: conchas ovais em superelipse, mais largas embaixo e inclinadas; lateral afinando até uma placa plana; arco único grosso com luvas; haste deslizante com anéis; braço único até uma dobradiça. Toda a geometria é gerada em código; nenhuma imagem ou malha de terceiros é embutida, e não há logo nem texto de marca. O anel de 48 LEDs não existe no fone real; ficou no vão entre a lateral e a placa porque o app usa o anel para bateria e modo. |
| 38 | **Torno oval (`ovalLathe`) com normal analítica para superfícies homotéticas** | O perfil (r, y) escala um contorno superelíptico; a normal é `(nr / (N·S))·N + ny·Y`, exata para esse tipo de superfície. O toro e a caixa arredondada saíram (sem uso). 23,5 mil triângulos. |
| 39 | **Painel desacoplado: `PanelView(state:actions:)` + `MenuBarView` como adaptador** | Permite previews e render para PNG sem fone nem `DeviceController`. Nenhuma lógica de protocolo mudou. |
| 40 | **"Tocando agora" fica escondido** | O protocolo v2 tem a mensagem `PlaybackName` (título/artista) nas referências, mas o `MDRKit` não a decodifica, e o prompt proíbe mexer no protocolo. A UI já tem a linha (`PanelState.nowPlaying`); ela aparece quando o decodificador existir. |
| 41 | **Fundo: `glassEffect` no macOS 26+, `NSVisualEffectView(.popover, .active)` antes, sólido com Reduzir transparência** | O `MenuBarExtra` também tem fundo próprio; o nosso fica por cima e cobre o conteúdo das janelas de trás. **Substituída pela #62.** |
| 42 | **Snapshot do painel com substitutos desenhados** | O `ImageRenderer` não desenha NSViews (switch, `Menu`, `RealityView`, material). No modo `panelSnapshot` eles viram desenhos SwiftUI equivalentes e o modelo vira um render do SceneKit. No app real são os controles nativos. Os PNGs são gerados com `Quietbar --render-panel-previews /tmp/quietbar-ui`. |
| 43 | **Localização (String Catalog, PT-BR fonte + EN) cobre o painel** | As outras abas das Configurações continuam só em PT-BR; traduzi-las fica para quando houver demanda. Os nomes de preset seguem o idioma do sistema (`String(localized:)`). |
| 44 | **Contraste alto: fundo do módulo mais claro + borda forte** | Com o fundo do card cheio, o texto secundário perdia contraste (visto no render). |
| 45 | **Modelo calibrado contra as vistas de referência, lado a lado** | Vista frontal e lateral em teleobjetiva (`--view front|side`, quase ortográficas como o desenho de referência) comparadas com as imagens. Ajustes: conchas grandes (≈ 54% da largura do arco) e fundas (carcaça ≈ 2× a almofada), inclinadas 30° com a base para dentro; almofada de seção superelíptica; arco quase semicircular e grosso; braço por fora, terminando na borda superior da carcaça (placa livre). O enquadramento padrão do app passou a ser a foto clássica do XM5: 3/4 pela esquerda, um pouco de baixo, com a placa esquerda de frente. |
| 46 | **Anel de luz do modelo: opcional e desligado por padrão** (Configurações › Popup › "Anel de luz no modelo") | O XM5 real não tem anel de luz, e ele tirava a semelhança. Sem anel, a placa cresce até quase a borda e o vão vira uma costura de ~1 mm, com a placa no mesmo acabamento fosco da carcaça (antes ela lia como um "buraco" preto). Bateria e modo continuam no painel e no popup. Com o anel ligado, volta o comportamento anterior (48 segmentos, cor configurável). |
| 47 | **RealityKit ganhou luz direcional e IBL mais forte** | O render do app (RealityKit) saía bem mais escuro que o do SceneKit e o preto fosco perdia o volume; conferido lado a lado pelo `RealityRenderer`. |
| 48 | **Ícone do app gerado a partir do modelo 3D** (`mdr-cli model --icon App/Resources/Assets.xcassets/AppIcon.appiconset`) | Fone na pose 3/4 do app sobre o squircle da grade de ícones do macOS (1024, área de 824, sombra própria). Fundo cinza-claro neutro, sem azul, para o fone preto ter contraste. Os PNGs ficam versionados; o comando regera depois de mudar o modelo. Asset catalog clássico em vez de `.icon` do Icon Composer (macOS 26): funciona do 14 em diante sem ferramenta extra. |
| 49 | **Modelo 3D do RealityKit em cache e aquecido na abertura do app** | Medido (`mdr-cli bench`, release): a IBL custava ~0,7 s e as malhas 70–180 ms **a cada abertura do painel**. Agora IBL e um protótipo do modelo são gerados uma vez, em segundo plano, quando o app abre; cada view clona o protótipo (3–5 ms) e religa a IBL ao próprio container. O `RealityView` carrega de forma assíncrona: o painel abre na hora e o 3D aparece quando o clone fica pronto. |
| 50 | **Cor de destaque: o painel usa `Color.accentColor`, que segue Ajustes › Aparência › Cor de destaque** | Com "Multicolor" (a chave `AppleAccentColor` ausente), o macOS usa o azul padrão do app. Não há cor fixa no código do painel. |
| 51 | **Mini curva do EQ inclui o Clear Bass como primeiro ponto** | No XM5 real o preset "Graves realçados" é Clear Bass +7 com as 5 bandas em 0 (lido no fone); só com as bandas a curva saía reta. |
| 52 | **Nome do fone: `title3` → `headline` → 2 linhas** | Nomes personalizados longos (ex.: "Fone do Raphael") não cabem numa linha ao lado do 3D de 84 pt e do anel de bateria; quebrar é melhor que cortar. |
| 53 | **Nome neutro: Quietbar** (antes "SonyCtl") | O nome antigo usava a marca Sony; "MyXM5Control", sugerido, ainda carregaria a designação de produto "XM5". Quietbar não usa marca de terceiros. O README cita o WH-1000XM5 só para descrever compatibilidade. Mudaram também o bundle ID (`io.github.raphaeltorquat0.Quietbar`), as notificações internas e as pastas de dados (`~/Library/Application Support/Quietbar`, `~/Library/Logs/Quietbar`). Os módulos `MDRKit`/`MDRTransport`/`MDRSession` e o `mdr-cli` mantêm o nome do protocolo (MDR), como as referências. |
| 54 | **Outros fones: só MDR v2 nesta etapa** | XM6, CH720N, ULT, WF-1000XM4/XM5/XM6, WF-C*, LinkBuds falam o mesmo MDR v2 do XM5. WH-1000XM4/XM3/XM2, WF-1000XM3 e WF-SP800N usam MDR v1 (outro UUID, outro codec, booleanos invertidos, RET antes do ACK no XM3) e ficam para uma etapa própria; sem captura pública do XM4, ele seria experimental de qualquer forma. |
| 55 | **Bateria de earbuds: esquerda/direita (`0x01`/`0x09`) e estojo (`0x02`/`0x0A`)** | Layout conferido no libmdr e nas capturas reais do WF-1000XM5 e do LinkBuds Clip (testes byte a byte, inclusive um nível escapado no fio). O lado com nível 0 é tratado como ausente; a "bateria principal" (ícone, aviso, popup) é a única do over-ear ou o lado mais fraco presente; o estojo não conta. |
| 56 | **EQ de N bandas: 6 (Clear Bass + 5, ±10 dB) e 10 (31 Hz–16 kHz, ±6 dB)** | O número de bandas sai da resposta do fone, como no libmdr. O `precondition` de 5 bandas (que derrubaria o app num LinkBuds) saiu. Aplicar preset continua sem mandar bandas (senão o fone vira Custom). Presets salvos guardam a curva completa e só aparecem para fones com o mesmo número de bandas. |
| 57 | **Perfil de fallback só para o WH-1000XM5** | Antes, qualquer fone que não respondesse à lista de funções herdava o perfil do XM5, e um timeout só na T2 apagava a T1 que já tinha chegado. Agora a T1 recebida fica, e o perfil só é usado se o modelo for o XM5 (ou ainda desconhecido). |
| 58 | **NC `0x16` (dual/single) e modos de escuta dos LinkBuds ficam fora** | O `0x16` tem outro layout (6 campos) e nenhuma captura pública para validar; modos de escuta (BGM, Voice Boost) são uma feature à parte. Fones só-ambiente (`0x22`) mostram só Ambiente/Desligado; sem NC, o módulo de modo some. |
| 59 | **Earbuds usam o SF Symbol `earbuds` no lugar do 3D** | O modelo 3D é de um over-ear; um modelo de earbuds e estojo fica para depois. Um `.usdz` ou imagem do usuário continua tendo prioridade. |
| 60 | **Bug corrigido: EQ com função `0x53` pedia o tipo `0x03`, que o decoder rejeitava** | O decoder de presets agora aceita `0x03` com o mesmo layout; se um firmware divergir, o decode devolve nil como antes. |
| 61 | **`NSStatusItem` + `NSPanel` próprios no lugar do `MenuBarExtra`** | No macOS 26+ o `MenuBarExtra(.window)` põe um vidro de fundo na janela pelo WindowServer (fora da árvore de camadas do app; nem `containerBackground(.clear, for: .window)` tira), o que obrigava vidro sobre vidro. Com item e painel próprios: clique abre/fecha, clique direito ou Option-clique mostram o menu curto (verificado com clique real no macOS 27; o monitor da #26 não via esses cliques), clique fora e Esc fecham. O item de status é desenhado fora do processo: o clique nele também chega ao monitor global (ignorado pela área do ícone) e o Option vem de `NSEvent.modifierFlags`. `openSettings` só existe dentro de uma view SwiftUI; antes do painel abrir pela primeira vez, uma janela de 1 pt fora da tela faz a ponte. |
| 62 | **Liquid Glass no estilo da Central de Controle (macOS 26+)** | Sem fundo no painel: cada módulo é uma plataforma `glassEffect` solta (raio 22). Modo de som em três blocos de vidro interativos, o ativo com círculo branco e símbolo na cor de destaque, como os botões ligados da Central de Controle. Slider nativo (envia ao soltar; teclado e VoiceOver a cada passo); rodapé com botões `.glass`. Nada de vidro dentro de vidro (o "Conectar" fica `.borderedProminent`). No macOS 14/15 e no snapshot do `ImageRenderer`, o visual anterior (material `.popover`, cartões cinza). Popup de conexão também em `glassEffect`. Conferir com `Quietbar --demo-panel <caso>` / `--demo-popup` e `screencapture`. |
| 63 | **Tamanho da janela do painel calculado pelo app** | Com `sizingOptions = .preferredContentSize`, certas alturas fracionárias faziam o `NSHostingView` redimensionar a janela em laço até estourar a pilha (crash visto no estado "desconectado"). O painel mede a view (`fixedSize` + `onGeometryChange`), arredonda para cima e só redimensiona quando o tamanho muda, mantendo o topo sob a barra. |
